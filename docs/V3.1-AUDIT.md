# V3.1 audit: UX, realism and presentation pass

Scope: the V3.1 instructions. This is polish and realism, not a feature phase. Each screen and workflow was inspected in the browser (360 px, 390 px, 768 px, 1024 px, 1280 px) and in code before changes were made. Severity follows the brief:

- **Critical:** misleads, harms research validity or privacy, or blocks a task.
- **Major:** meaningful usability, comprehension or trust issue.
- **Minor:** polish.

## Findings and resolutions

### Critical

| # | Finding | Resolution |
|---|---|---|
| C1 | `VERIFIED` / `OFFICIAL` badges implied that a restaurant had verified or published fictional nutrition | Labels are now **DEMO VERIFIED** / **DEMO OFFICIAL** ("Simulated partner data" / "Simulated published data"), with sheets that say the data is simulated. `OFFICIAL` is reserved for genuinely authoritative data (none exists). The model receives the same labels |
| C2 | Adding real restaurants risked presenting real businesses as partners, or attaching invented menus, prices and ordering to them | **Hybrid (user decision):** real restaurants carry verified identity and location only (`identity: "real"`). They have **no** menu, prices, nutrition, hours, pickup or ordering, are marked "Real · not affiliated", and MacroAgent refuses to invent their menu and offers "Scan the menu here". Demo brands keep all simulated data and are tagged DEMO. Tests enforce this |
| C3 | A desktop product-demo video beside the phone would show **baseline participants** the treatment | The showcase and presenter controls render only at ≥ 1024 px and **never** during a trial or on `/experiment` or `/baseline` |
| C4 | Privacy notice and map attribution said "all restaurants are fictional", which becomes false with real restaurants | Rewritten: what is real (name and location, verified 2026-09-29, sources), what is simulated, and OSM attribution |

### Major

| # | Finding | Resolution |
|---|---|---|
| M1 | The agent's busy state was one generic line ("Checking menus and running the optimizer…"), whatever it was doing | Real step states: live progress reports each model call and tool as it runs ("Understanding request → Checking restaurants → Optimizing supported configuration → Writing reply → Checking constraints"). Each reply shows a completed-steps checklist mapped 1:1 to tool calls and the VERIFY check. No reasoning traces |
| M2 | Map pin → card: selecting a pin highlighted a card that could be off-screen | The selected card scrolls into view (smooth, or instant under reduced motion). Pin ↔ card selection stays in sync |
| M3 | Pins for places in the same food court (Sally's Salads and Mozza) hid each other | Pixel-space label collision pass after each zoom. Pins keep true coordinates and labels stack. No overlaps at zoom 14–16 |
| M4 | 640–1023 px screens showed a shrunken desktop device frame | Below 1024 px only the app renders (full height, max 520 px wide): no shell, title or video |
| M5 | Opening the agent at a restaurant without menu data would have produced "Nothing here fits" | Honest real-restaurant context message with a **Scan the menu here** action. The scan carries the restaurant through and the IndexedDB record is tagged. The offline sample says "not <restaurant>'s menu" |
| M6 | **Reset demo** didn't clear the agent conversation (stale chat on Demo Day) | A reset counter (`demoEpoch`) resets the agent session |
| M7 | No way to record the exact agent configuration for the freeze (§11) | `/research` → **Freeze record values**: app commit, server-side model ID, SHA-256 of system prompt + tool schemas + model settings, fallback policy, and device settings. One-tap copy |

### Minor

| # | Finding | Resolution |
|---|---|---|
| m1 | "N tool calls" jargon under replies | Replaced by the step checklist. Raw tool names sit behind "Tool details" |
| m2 | Staggered entry animations kept `animation-delay` under reduced motion (content hidden up to ~300 ms) | Reduced motion now also zeroes delays. Chat scrolling respects reduced motion |
| m3 | Home "How MacroTable works" still described the V2 flow | Updated for MacroAgent and pickup/in-store approval |
| m4 | Agent composer didn't grow for longer messages | Auto-grows up to ~5 lines |
| m5 | Simulated pickup times looked factual | Labelled "(simulated)". Real restaurants show none |

## Verified after changes

- Type-check.
- 90 automated tests.
- Production build.
- Layout at 360 / 390 px: app only, no showcase or video element, no horizontal overflow on any screen.
- Layout at 768 px: app only. At 1024 / 1280 px: phone plus showcase (placeholder), balanced margins, no overflow.
- Participant routes (`/baseline`, `/experiment`) at desktop width: no showcase.
- Explore: real (dashed) and DEMO pins, pin → card scroll, OSM attribution, disclosure line.
- Agent: canonical request → DEMO VERIFIED 682 kcal / 49 g / €16.50 with steps; real restaurant → honest message → scan → offline sample labelled "not Mozza's menu".
- Approve → pickup code. Reset demo clears the chat.
- Baseline lists only the three demo menus.
- Camera: the browser pane blocked capture, so upload was used (no real hardware).
- Keyboard: map pins are focusable markers, and every control is a native button or link with a visible `:focus-visible` outline.

## Research validity

- Baseline is unchanged in content. It only lists restaurants with menus (the same three demo menus as before). No agent, ranking, optimizer guidance, "why this fits", provenance assistance or showcase was added.
- Treatment-specific changes are:
  - agent step states and checklist;
  - DEMO labels (also visible in treatment meal screens);
  - real restaurants on the Explore map (treatment only);
  - Scan-the-menu-here action;
  - reset fix.
- They change the treatment UI, so V3.1 is its own pilot version: don't pool it with V3.0 pilot data. See `docs/study/`.
- Generic fixes that apply to both conditions: reduced-motion delay fix, layout breakpoint.

## Still unverified

- **Real iPhone Safari and Android Chrome:** not tested. See `docs/study/smoke-test.md`.
- **Live Gemini:** the proxy isn't deployed yet, so the agent runs in offline-demo mode everywhere.
- **Real camera hardware:** not tested. The browser pane blocks camera access.
